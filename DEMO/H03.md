# H03 — rekrutacja i kolejka zgłoszeń

Dokument opisuje scenariusz demonstracyjny na danych fikcyjnych. Nie zawiera
prawdziwych danych osobowych ani prawdziwych adresów e-mail.

## Dane i uruchomienie

- konto administracyjne: `admin@demo.pl` (hasło demo z lokalnego `.env`),
- przykładowe zgłoszenie: `kandydatka@example.test`, status `new` (utwórz ręcznie lub fabryką),
- API: `http://localhost:8000/api/v1`, frontend: `http://localhost:3000`.

Po uruchomieniu środowiska:

```bash
bash scripts/setup.sh
docker compose exec app php artisan test --filter=ApplicationModelTest
cd frontend && npm run lint && npm run build
```

## Scenariusz lokalnego kontraktu

1. Otworzyć panel administracyjny i zakładkę „Zgłoszenia” po podłączeniu
   `h03ApplicationsTabSlot` przez właściciela H18 (do czasu podłączenia uruchomić
   komponent w izolowanym ekranie deweloperskim).
2. Sprawdzić kolejkę, szczegóły i bezpieczny wgląd w skan dyplomu.
3. Utworzyć zgłoszenie ręcznie lub zaimportować CSV; sprawdzić raport
   `imported`/`skipped`.
4. Zaakceptować zgłoszenie, odczytać symulowane zaproszenie w Mailpit, użyć
   `POST /api/v1/auth/activate`, a następnie zalogować się nowym kontem.
5. Odrzucić inne zgłoszenie z obowiązkowym powodem i sprawdzić audyt oraz
   powiadomienie.
6. Powtórzyć akceptację przy pełnej edycji: bez `force` oczekiwany jest
   `edition_capacity_exceeded`, a po jawnym potwierdzeniu `force` akceptacja
   może przekroczyć limit.
7. Sprawdzić konflikt z istniejącym adresem e-mail oraz brak publicznej
   trasy samodzielnej rejestracji. Dodatkowe decyzje API są lokalnym override'em
   zaakceptowanym przez użytkownika i wymagają synchronizacji przez strażnika.

## Stan obecny implementacji

Backend i komponent slotu są gotowe: kolejka, create, szczegóły, accept/reject,
capacity/force, import CSV, zaproszenie aktywacyjne i logowanie wglądu w skan.
Zakładka jest dostępna jako `h03ApplicationsTabSlot`; produkcyjne osadzenie na
`/admin/uczestniczki` nadal wykonuje właściciel H18.

Lokalne decyzje payloadów i dodatkowych tras opisano w `design.md`. Wdrożenie
korzysta wyłącznie z danych fikcyjnych i symulowanych e-maili.

## Checklista dostępności slotu

- [x] Treści są zwykłym tekstem Reacta; brak `dangerouslySetInnerHTML`.
- [x] Komponent korzysta z istniejącej karty z nagłówkiem i semantycznym tekstem.
- [x] Kolor nie jest jedynym nośnikiem informacji.
- [x] Slot nie przechwytuje fokusu i nie wprowadza niedostępnej interakcji.
- [x] Klawiatura: slot nie ma akcji wymagających dodatkowej obsługi fokusu.
- [x] Mobile: karta używa płynnego układu bez stałej szerokości ani poziomego
      przewijania.
- [x] `npm run lint` i `npm run build` przechodzą.
- [x] Dialogi, formularze i akcje decyzji mają etykiety ARIA, obsługę Escape,
      stan pending i osobne potwierdzenie `force`.
- [ ] Weryfikacja na ekranie H18 — po podłączeniu adaptera przez właściciela
      H18.
