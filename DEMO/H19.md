## Co działa

**Backend — `routes/api/h19.php` (flaga `features.h19`), pod `auth:sanctum` +
`role:project_manager,super_admin`:**

| Metoda | Trasa | Zachowanie |
|---|---|---|
| `GET` | `/api/v1/admin/dashboard` | `data.counters` (`participants`, `completed`, `certificates`) + `data.queues` (`applications`, `internship_entries`, `profiles`, `questions`), każda z `key`/`count`/`link` |
| `GET` | `/api/v1/admin/edition` | aktywna edycja: `name`, `starts_at`, `ends_at`, `seats_limit` + komplet kluczy §3.3 |
| `PATCH` | `/api/v1/admin/edition` | częściowa aktualizacja tych samych pól, walidacja zakresów, audyt `edition.updated` |

- **Liczniki i kolejki** (`app/Services/H19/DashboardSummary.php`) — proste zapytania `COUNT`
  (nie przez `ProgressAggregator`, który liczy jedną osobę naraz). Zapytania dokładnie
  zgodne z `tests/Feature/SeedIntegrityTest::test_dashboard_and_report_counters_match_the_seed`
  (już istniejącym w starterze) — w tym `InstructorQuestion::whereNull('answer')`, nie
  `answered_at`.
- **Zapis ustawień** (`app/Services/H19/EditionSettingsUpdater.php`) — `Settings::edition()`
  jest tylko-do-odczytu (sygnatura zamrożona), więc zapis idzie bezpośrednio przez
  `Edition::update()` w transakcji + `AuditLog::record(..., 'edition.updated', $edition,
  ['changed' => [...]])`.
- **Walidacja** (`app/Http/Requests/H19/UpdateEditionRequest.php`) — pola procentowe
  (`test_pass_threshold`, `reliability_threshold`, `lesson_completion_percent`) 0–100;
  pola licznikowe ≥1; `ends_at` po `starts_at`.
- Dodano `HasFactory` do `App\Models\Edition` (brakowało w starterze) + nowy
  `database/factories/EditionFactory.php` — potrzebne do testów H19, do użytku też przez
  inne pakiety.

**Frontend — `#/admin` i `#/admin/ustawienia`:**

- `/admin` (`app/(administracja)/admin/page.tsx`) — trzy kafle liczników + lista kolejek;
  każdy wiersz kolejki to link (`next/link`) prowadzący do `link` z odpowiedzi.
- `/admin/ustawienia` (`app/(administracja)/admin/ustawienia/page.tsx`) — formularz w
  dwóch kartach („Edycja” i „Reguły programu”); błędy 422 mapowane na pola; komunikat
  sukcesu po zapisie.
- Wpis menu „Ustawienia” dodany do `lib/menu/admin/{h19-ustawienia.ts,index.ts}` (plik
  H19-owned, samo-rejestrujący się — bez zgłoszenia do sztabu).

## Jak pokazać (scenariusz ręczny)

Wymagane: `docker compose up -d --wait`, `cd frontend && npm run dev`.

1. **Logowanie** — http://localhost:3000/logowanie → `admin@demo.pl` / `admin1234`
   (lub `opiekun@demo.pl` / `admin1234`, rola `project_manager`).
2. **Pulpit** (`/admin`) — trzy kafle: uczestniczki/uczestnicy = 3, ukończenia = 1,
   certyfikaty = 1. Lista kolejek: zgłoszenia = 1, staż = 2, profile = 0, pytania = 1.
3. Kliknij wiersz kolejki „Zgłoszenia rekrutacyjne” → przejście do `/admin/uczestniczki`
   (ekran H18/H03).
4. **Ustawienia** (`/admin/ustawienia`) — zmień „Próg zaliczenia testu (%)” na `150` →
   **Zapisz zmiany** → błąd walidacji przy polu, wartość nie zapisana.
5. Zmień próg na `90` → **Zapisz** → zielony komunikat „Zapisano zmiany.”. Odśwież stronę
   — wartość się utrzymuje.
6. **Rola bez dostępu:** zaloguj się jako `marta@demo.pl` (wolontariuszka), spróbuj
   `GET /api/v1/admin/dashboard` → `403 forbidden`.

> Krok 6.3 z `openspec/.../tasks.md` (pełne ręczne przejście w przeglądarce, w tym
> przegląd klawiaturą obu ekranów) **nie zostało jeszcze wykonane w tej sesji** — backend
> potwierdzony testami, frontend potwierdzony `npm run build`, ale nie klikany ręcznie.

## Testy / lint / build

Weryfikacja wykonana w **osobnym git worktree** (`../psychon-hackaton-h19`, gałąź
`pakiet/H19-pulpit-i-ustawienia`), bo równolegle w katalogu głównym repo działa inna
sesja nad H14 na tej samej maszynie. Kontener `np_app` ma bind-mount do katalogu
głównego, więc backend zweryfikowano, tymczasowo kopiując wyłącznie nowe pliki H19
(bez kolizji ze ścieżkami H14) do katalogu głównego, uruchamiając testy i sprzątając
kopie zaraz po — katalog główny wrócił do stanu sprzed kopiowania (`git status`
niezmieniony poza plikami H14).

```
docker compose exec app php artisan test --filter=H19
  → 10 passed (56 assertions)

docker compose exec app ./vendor/bin/pint --test <pliki H19>
  → 1 problem znaleziony i naprawiony (EditionResource.php), potem czysto

cd frontend && npm ci && npm run lint -- --fix   → czysto
cd frontend && npm run build                     → OK, /admin i /admin/ustawienia zarejestrowane
```

Pełny `docker compose exec app php artisan test` (cały pakiet, razem z H01/H14) **nie
został uruchomiony** w tej sesji — do zrobienia przy integracji, żeby wykluczyć
interferencję z równoległą pracą nad H14 na tej samej bazie `niepodzielni_testing`.

## Czego brakuje / świadome decyzje

- **Linki kolejek do ekranów spoza H19** (`/admin/staz`, `/admin/profile`,
  `/panel/prowadzacy`) wpisane na sztywno w `DashboardSummary` — do uzgodnienia z
  właścicielami H11/H15/H09/H17 przy integracji; to zwykłe stringi, nie blokują
  działania H19 samodzielnie.
- **Test wspólny H19+H10** (§6.3 dokumentu zależności: „próg z ustawień") — H19 dostarcza
  tylko mechanizm (brak cache'a); pełny test integracyjny z podejściem do testu czeka na
  H10.
- **Slug 409** — nie dotyczy H19 (brak operacji tworzenia unikalnego zasobu w tym
  pakiecie).
- **Dług: `HasFactory` na `Edition`** — zmiana w pliku poza wyłączną własnością H19
  (`app/Models/Edition.php`); niewielka, addytywna, bez zmiany zachowania — do
  potwierdzenia przy przeglądzie łącznika, że to akceptowalne.
- **Brak pełnego ręcznego przejścia w przeglądarce** — patrz sekcja „Jak pokazać”, krok 6.
