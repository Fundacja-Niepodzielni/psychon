## Co działa

**Backend:**

| Plik | Rola |
|---|---|
| `app/Http/Middleware/EnsureAccessActive.php` | już istniał w starterze (403 `access_expired` na żywo, sprawdzenie `program_completed_at` znosi limit) — **nietknięty**, H04 tylko go wykorzystuje i testuje |
| `app/Http/Controllers/Api/V1/Admin/AccessController.php` | `POST /admin/users/{id}/extend-access` — `{months}` (sumuje się z jeszcze aktywną datą) albo `{until}` (ustawia wprost) |
| `app/Http/Requests/H04/ExtendAccessRequest.php` | dokładnie jedno z `months`/`until` (`required_without` + `prohibits`) |
| `app/Console/Commands/CheckExpiredAccess.php` | `php artisan access:check-expired` — zadanie cykliczne (zaplanowane `->daily()` w `routes/console.php`) |

- Trasa: `POST /admin/users/{id}/extend-access`, `role:project_manager,super_admin`.
  Audyt `access.extended` (kto = `actor_id`, komu = `subject_id`/`subject_type`, do kiedy =
  `details.access_expires_at`, plus `details.previous_access_expires_at` dla kontekstu).
- `access.active` middleware **już jest podpięty przez inne pakiety** do ich własnych tras
  treści programu — widać to w kodzie (`grep`): H06 (lekcje), H10 (testy), H11 (staż), H13
  (certyfikat), H14 (dokumenty). H21 i H01 **świadomie go nie używają** — obie mają w swoich
  plikach tras komentarz „criterion 2, shared test with H04", czyli inne zespoły już
  przygotowały wyjątki i czekały na testy H04.
- `zadanie cykliczne`: blokowanie dzieje się **na żywo** w middleware (liczone przy każdym
  żądaniu z `access_expires_at`), więc zadanie cykliczne niczego nie musi „domykać". Zamiast
  wymyślać nowy slug audytu/powiadomienia (żadnego nie ma w rejestrze §3.2/§3.1 dla samego
  wygaśnięcia — `access.expiring_30d/7d` to jawnie pozycja post-hackathonowa), zadanie loguje
  (`Log::info`) liczbę i id kont z wygasłym dostępem — widoczność operacyjna bez naruszania
  zamrożonych rejestrów.

## ⚠️ Świadome ograniczenie zakresu — bez zmian w plikach innych pakietów

W przeciwieństwie do H02 (gdzie kryterium ★ wprost wymagało ekranu 403 i nie było innej
drogi), **żadne** z trzech kryteriów H04 nie wymaga zmiany w cudzym pliku:

- **„data wygaśnięcia widoczna w profilu"** jest w opisie zakresu pakietu, ale nie jest
  ponumerowanym kryterium akceptacji. Dane **już są** zwracane przez `GET /me`
  (`ProfileResource.php`, pole `access_expires_at` — zbudowane przez H01) i już otypowane
  we froncie (`panel/profil/page.tsx:28`), ale nieujęte. Wizualne dodanie tego pola to jedna
  linijka w cudzym, scalonym, `DONE` pliku H01 — celowo **nietknięte** tutaj. Gotowy fragment
  dla właściciela H01 (albo integracji):
  ```tsx
  {profile.access_expires_at && !profile.program_completed_at && (
    <p className="text-caption text-subtle">
      Dostęp do materiałów do:{" "}
      {new Date(profile.access_expires_at).toLocaleDateString("pl-PL")}
    </p>
  )}
  ```
- **Panel admina „przedłużanie dostępu"** (matryca uprawnień, wiersz „Panel: przedłużanie
  dostępu") nie ma dziś żadnego miejsca w UI — H04 nie ma własnego `Ekrany` w
  `01-pakiety-zadan.md`, a karta osoby (H18, gdzie taki przycisk naturalnie by usiadł) jest
  wciąż `GOTOWE`/nieprzypisana. Endpoint (`POST /admin/users/{id}/extend-access`) jest gotowy
  i przetestowany — podpięcie przycisku to zadanie H18, gdy powstanie.

Jedyna zmiana w pliku poza `routes/api/h04.php` to `frontend/lib/api.ts` — bezpośrednie
lustrzane odbicie już istniejącego wzorca (401→`/logowanie`) w tym samym pliku, dla ekranu,
który już istniał w starterze (`app/dostep-wygasl/page.tsx`).

## Jak pokazać (scenariusz ręczny)

Wymagane: `docker compose up -d --wait`, `cd frontend && npm run dev`.

1. **Backend, w izolacji:** `docker compose exec app php artisan test --filter=AccessExpiry`
   → 25 passed.
2. **API wprost — blokada:** utwórz konto z `access_expires_at` w przeszłości (np. przez
   tinker, jak w tym pakiecie) → `GET /api/v1/documents` → `403 access_expired`; `GET
   /api/v1/me` i `GET /api/v1/onboarding` → `200`.
3. **API wprost — przedłużenie:** zaloguj się jako `admin@demo.pl` / `admin1234` →
   `POST /api/v1/admin/users/{id marty}/extend-access {"months":6}` → `200` z nową
   `access_expires_at`; sprawdź `audit_log` (kolejny wpis `access.extended`).
4. **Front — ekran wygaśnięcia:** dla konta z wygasłym dostępem dowolne żądanie do trasy
   gated (np. otwarcie `/panel/dokumenty`, gdy H14 wywoła `GET /documents`) przekierowuje
   na `http://localhost:3000/dostep-wygasl` (ekran startera „Twój dostęp do platformy
   wygasł").
5. **Zadanie cykliczne:** `docker compose exec app php artisan access:check-expired` →
   log w `storage/logs/laravel.log` z liczbą i listą id kont z wygasłym dostępem (albo
   „Brak kont z wygasłym dostępem.").

## Czego brakuje / świadome decyzje / follow-upy

- **Pole daty wygaśnięcia w `/panel/profil`** i **przycisk „przedłuż dostęp" w karcie
  osoby** — gotowe fragmenty/endpoint, wpięcie należy do H01 (`DONE`) i H18
  (`GOTOWE`/nieprzypisany) odpowiednio; patrz sekcja wyżej.
- **`matrix_5d` w H02** (`tests/Feature/PermissionMatrix/PermissionMatrixTest.php`) można
  teraz odblokować (nie jest już `skipped` z braku pakietu — H04 istnieje). To zmiana w
  pliku H02, nie H04; zgłaszam jako follow-up zamiast dotykać cudzy plik z tej gałęzi.
- **H06/H10 (lekcje/testy) nie są w automatycznej macierzy** `AccessExpiryEnforcementTest` —
  ich trasy wymagają `Course`/`Lesson`/`Test`, a te modele nie mają jeszcze fabryk w repo.
  Bramkowanie jest widoczne wprost w ich plikach tras (`access.active` w grupie); pełne
  pokrycie należy do testów tych pakietów.
- **Brak testów frontendu** — jak w H01/H02: repo nie ma runnera JS; przekierowanie
  zweryfikowane `npm run build` + ręcznie przez API (patrz scenariusz) — nie było dostępnej
  automatyzacji przeglądarki w tym środowisku na zrzuty ekranu.
- **`until` bez ograniczenia `after:now`** — świadomie: admin może chcieć skorygować datę
  wstecz (np. pomyłka), kontrakt tego nie zabrania.
