## Co działa

**Backend — `routes/api/h16.php` (flaga `features.h16`):**

| Metoda | Trasa | Zachowanie |
|---|---|---|
| `GET` | `/api/v1/notifications` | lista własnych powiadomień (paginacja), `meta.extra.unread` |
| `POST` | `/api/v1/notifications/{id}/read` | oznacza jako przeczytane; cudzy `id` → `404 not_found` |
| `POST` | `/api/v1/notifications/read-all` | oznacza wszystkie własne nieprzeczytane jako przeczytane |
| `GET` | `/api/v1/admin/emails` | skrzynka e-maili symulowanych; `role:project_manager,super_admin` |

- `Notify::send` (starter, niezmieniony) tworzy jednocześnie wiersz `notifications` i `emails`
  (`status: simulated`) w jednej transakcji — H16 tylko czyta i wystawia te dane.
- `NotificationController`, `Admin\EmailController`, `NotificationResource`, `EmailResource` — nowe.
- Nikt poza właścicielem nie widzi cudzego powiadomienia (404, nie 403 — zgodnie z §1.1 kontraktu).

**Frontend:**

- `components/notifications/NotificationBell.tsx` — dzwonek w `PanelShell.tsx` (wszystkie panele):
  licznik nieprzeczytanych, lista z pollingiem co 30 s, klik = nawigacja pod `link` + oznaczenie jako
  przeczytane, przycisk „Oznacz wszystkie jako przeczytane".
- `app/(administracja)/admin/emails/page.tsx` — skrzynka e-maili (tylko administracja, wpis w
  `lib/menu/admin/h16-emails.ts`): tabela odbiorca/temat/status/czas + podgląd e-maila w modalu
  (From/Do/Temat/Treść).

## Jak pokazać (scenariusz ręczny)

Wymagane: `docker compose up -d --wait`, `cd frontend && npm run dev`.

1. **Logowanie** — http://localhost:3000/logowanie → `marta@demo.pl` / `demo1234`.
2. Dzwonek w nagłówku pokazuje badge **„1"** (nieprzeczytane).
3. Klik na dzwonek → lista 3 powiadomień: `course.unlocked` i `internship.accepted` (przeczytane),
   `internship.returned` (nieprzeczytane, wytłuszczone, kropka).
4. Klik na `internship.returned` → przejście na `/panel/staz`, badge znika (0 nieprzeczytanych).
5. Wyloguj się, zaloguj jako `admin@demo.pl` / `admin1234`.
6. Menu boczne → **Skrzynka e-maili** (`/admin/emails`) → 3 wiersze dla `marta@demo.pl`, status
   „Symulowany". Klik **Podgląd** → modal z From/Do/Temat/Treść.
7. **Izolacja (opcjonalnie, API):** zaloguj się jako `marta@demo.pl`, spróbuj
   `POST /api/v1/notifications/{id cudzego powiadomienia}/read` → `404 not_found`.

## Czego brakuje / świadome decyzje

- **Brak testów frontendu** — repo nie ma runnera JS; ekrany pokryte `npm run build` + scenariuszem
  ręcznym powyżej, oraz weryfikacją API na żywo (PowerShell) opisaną w historii pakietu.
- **Podgląd e-maila jako modal** — kontrakt nie definiuje `GET /admin/emails/{id}`; „podgląd" jest
  czysto frontendowy (dane już są w liście), zgodnie z zasadą nietworzenia nowych tras bez strażnika.
- **Szablon e-maila** — brak gotowego komponentu design systemu dla e-maili w repo; treść renderowana
  z `body_html` wygenerowanego przez `Notify::send` (`nl2br(e($body))`, bezpieczny escaped HTML).
- **Scalanie bez PR** — na wyraźną decyzję właściciela repo pakiet trafił bezpośrednio na `main`
  (zamiast `pakiet/H16-nazwa` → PR → review), z odstępstwem od `AGENTS.md` §„Commit & Pull Request”.
